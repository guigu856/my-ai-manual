# 通用写作方法论

跨平台、跨作品形态成立的写作方法。本文件从一次真实的“MCP Resources 文稿 → 短视频脚本”完整交互中提炼，再结合公开写作技能（oil-tone、workflow-producer、content-research-writer 等）与外部内容改写技能中可迁移的规则整理而成。每条规则都标注它解决的问题。

## 1. 输入理解：先分五要素

写作前先分离：平台、作品形态、内容主题、核心观点、额外要求。

常见错误是把它们混在一起：用户说“写个 AI 科普”时，“AI”是主题，“科普”接近形态但没说平台；“抖音 AI 科普 60 秒口播”才是一次可执行的输入。缺失影响成品结构的要素就问，不影响就先按上下文判断。

## 2. 观点提炼：找最值得讲的部分

从原始表达里找用户真正想说的，而不是用户可能想说的。

- 用户有一句话反复强调，它就是核心观点
- 用户提到了冲突或反差（“常见的是 X，被忽略的是 Y”），冲突点通常就是入口
- 用户没有表达的主张，不要替他补上
- 提炼结果写成一句“看完要记住什么”，作为全文主线

## 3. 主线纪律

全文服务核心问题。判断一句是否保留，问三件事：

1. 它推进核心观点吗？
2. 它解释观众必须知道才能理解的关键角色或机制吗？
3. 删掉它，观众会失去什么？

技术正确但偏离主线的细节（例如协议规范里的边角机制）在大众内容里是干扰，删除。标题问的问题必须是全文主线，不能只当外层包装。

## 4. 信息增量原则

每段必须让读者/观众知道新的东西。

- 同一结论换说法重复多次 = 冗余，压缩成一次
- “后半段信息增量不足”是常见失败：开头把结论都说完了，后面只剩复述
- 检查方式：把每段的唯一新信息写出来，重复的段删掉或合并

## 5. 开头：用最短篇幅进入主题

被忽略机制的引入方式（从真实交互验证有效）：

1. 先用观众熟悉的东西建立对照（“很多人把 MCP 理解成让 AI 调用外部能力”）
2. 指出被忽略的对象（“调用只是开始……Resources 就是这条连接”）
3. 第一屏/前几秒就进入主题，铺垫不超过整体的一小部分

开头过长的典型症状：观众听了十几秒还不知道这篇在讲什么。用户的原话是“感觉你前面讲那个工具讲太长了”，处理方式是直接砍掉前置解释。

用词要精确。用户会纠正概念命名（“忽略不是忘记”），所以不要用意义相近但不准确的词替换用户的概念。

## 6. 结构：问题 → 机制 → 关键边界 → 判断方法

观点短视频被验证有效的推进顺序：

- 问题/冲突：观众立刻意识到“为什么这个话题有必要”
- 机制：它是什么、怎么运作
- 关键边界：最容易被误解、最容易讲错的地方（通常也是最有价值的部分）
- 判断方法：观众能带走的一个可操作判断

反模式：均匀的“定义 → 解释 → 总结”循环重复多次。它听起来像完整教程，不像短视频。

## 7. 抽象概念的解释

- 类比：用“这有点像 X”降低理解门槛，但类比不能取代准确边界
- 关键角色给一句人话定义：出现“Client”“Host”“上下文”这类术语时，第一处就要用一句话解释它在这个话题里是什么
- 机制示例要准确：展示机制的具体实例（如 `project://rules/main-agent`）写进正文，这是机制的演示，不是装饰
- 自定义示例要标注：非官方标准的内容要说明“这是示例”，避免误导

## 8. 例子的规则

来自真实交互的两次否定：

1. “例子不要举我项目的例子，要举大众看得懂的” → 公开内容默认使用通用例子，用户的具体项目细节不写进去
2. “例子举得偏离实际应用方向了” → 例子要贴近主题的真实应用场景，而不是为了丰富随便加

结论：

- 例子必须服务于当前论点
- 例子要大众能看懂
- 同一处只留最有效的一个例子，不堆砌
- 涉及个人/项目信息时用通用化表述（除非用户明确要求写进去）

## 9. 金句与严谨性

记忆句（口诀式总结）有价值，但必须通过检查：

- 事实检查：口诀是否在技术上成立？
- 边界检查：它是否把复杂区别压成了错误二分？

真实案例：用户否定了“工具负责动作，资源负责材料”这个口诀，理由是“Tools 同样可以读取和返回信息，甚至返回资源链接”。更准确的说法是：两者差异在使用语义和控制方式——Tools 是模型可调用的能力，Resources 是由应用发现、读取和组织的上下文。

处理方式：金句可以保留，但要在技术上严谨的版本里保留；口诀导致错误理解时，修改口诀而不是保留错误表述。

## 10. 表达自然度与去 AI 味

- 口语化优先：参考真实口播转写稿的语气，不写书面报告腔
- 不用空洞营销词：“提升体验”“增强吸引力”“引发共鸣”这类无法指导判断的表述删掉
- 不写无来源的群体断言：“很多人第一次看到 X……”必须有来源，否则改成可验证的表述（如“X 很容易被理解成……”）
- 表达保持个人判断和口语节奏，不要把稿子修得过于光滑
- 结尾给一个可带走的判断，不喊口号、不拔高

## 11. 修改与自检：把用户否定过的问题变成检查项

以下问题在真实交互中被用户否定过，直接作为自检项：

| 被否定的写法 | 正确做法 |
|---|---|
| 开头铺垫过长，迟迟不进入主题 | 第一屏/前几秒进入核心对象 |
| 同一结论拆成多段反复解释 | 一段讲完，信息增量推进 |
| 标题只当包装，正文偏离标题的问题 | 标题问题即全文主线 |
| 为了“完整”加入用户没想表达的内容 | 只写用户想表达的 |
| 解释过度（讲协议边角细节） | 删除主线外细节 |
| 使用大众化套话、标准模板感 | 口语化、去模板 |
| 例子跑偏或堆砌 | 例子服务论点、大众可懂、只留最有效的 |
| 金句不严谨（错误二分） | 金句过事实/逻辑检查 |
| 把合理推测写成用户明确主张 | 推测必须标注 |
| 无来源的群体判断 | 删除或改成可验证表述 |

修改纪律：先诊断再动手。只改真正有问题的地方；不因为某个词“看起来像 AI 写的”就整段重写。

## 12. 证据三态

写作过程中涉及的事实，区分三种状态：

- 已确认：用户原话、已有稿件、可验证的公开资料
- 推导：从多个案例归纳出的原则，说明这是归纳
- 无法确认：明确说无法确认，不编造“看起来合理”的版本
