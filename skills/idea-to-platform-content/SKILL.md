# 想法 → 平台文稿 / 脚本

## 作用定位

输入：观点、想法、观察、碎片化表达、初步文稿、聊天记录或参考示例。

输出：符合指定**平台**与**作品形态**的 Markdown 文稿/脚本，既能被用户直接阅读修改，也能被下一步制作 Agent 继续执行。

先分清五类信息，不要混在一起：

1. 平台：抖音、小红书、X、公众号……（发布到哪里）
2. 作品形态：短视频脚本、口播稿、非口播画面脚本、图文、长文、推文/Thread、知识卡/工具卡（最终长什么样）
3. 内容主题：AI、创业、编程……（讲什么领域）
4. 核心观点：用户真正想表达的一句话
5. 额外要求：时长、语气、是否一稿多平台、禁止事项

## 第一步：确认平台与作品形态

开始写作前先判断这三项是否明确：

- 平台
- 作品形态
- 会影响成品结构的额外要求（如时长档位、是否口播）

判断规则：

- 三项都明确：直接开始，不要重复询问。
- 只缺平台：询问发布平台，因为画幅、字数、结构都可能不同。
- 平台明确但形态不明确，且该平台存在明显不同的形态：询问要哪一种。
- 用户上下文已经说得足够清楚：按上下文执行，不要机械提问。
- 默认只生成一个版本。只有用户明确要求“一稿多平台 / 全平台改写 / 批量生成”时才输出多版本，每个版本独立适配，不做“全平台通用稿”。

## 核心工作流

### 1. 输入盘点

列出已有的东西：原始表达、初稿、参考示例、聊天记录、历史版本。确认哪些是事实（用户原话、已有稿件、可验证资料），哪些是需要推导的。

### 2. 提炼核心观点

先写出一句“这篇内容看完后观众/读者要记住什么”，再动笔。找不到这句话时，回到用户原始表达里找最值得讲的部分，而不是把用户没想表达的内容补进来。

### 3. 确定主线

全文每一段都必须服务核心观点。与主线无关的细节删除，即使技术上正确（例如科普文里的协议边角细节会打断大众理解）。

### 4. 搭建结构与推进

按作品形态选择结构，读对应的格式 reference。通用原则：

- 段落必须推进信息，同一结论不要换着说法重复多次
- 后半段的信息增量不足，是冗余，不是强调
- 开头用最短篇幅进入主题（短视频尤其如此）
- 结论性判断放在最后，不提前总结

### 5. 写初稿

按格式 reference 的交付字段写。表达规则见 `references/writing-methodology.md`。

### 6. 做密度与自然度检查

- 删除无效解释和重复总结
- 检查金句是否经得起事实/逻辑检验
- 检查是否出现无来源的群体断言（“很多人以为……”这类话必须有出处或删掉）
- 检查是否为了“完整”加入了用户没想表达的内容

### 7. 平台与形态适配

读对应平台的 reference，按平台约束做最终调整。平台参数会变化：对字数上限、时长档位、规格等易变项，标注“经验值/需刷新”，不要写成永久规则。

### 8. 交付

输出 Markdown 文稿。结构按作品形态决定，不强制统一 Schema。文稿必须能让用户和下一步执行者看懂：标题/核心观点、正文分段、每段作用、可选的金句、可选视觉提示、下一阶段需要的信息。

## 边界

- 本 Skill 负责“文稿 / 脚本”，不替剪辑、动画或设计 Agent 写时间轴、镜头参数和动画参数。脚本里可以给出画面命题和视觉提示，粒度以“能推动下一阶段执行”为准。
- 不做观点之外的拔高。用户没主张的内容不写成用户的主张；“合理推测”要标注为推测。

## 自检清单（交付前）

- 平台、作品形态、核心观点三者是否清楚且被正确区分？
- 是否默认生成了全平台版本？（应为否，除非用户明确要求）
- 每段是否推进信息？是否存在换着说法重复同一结论？
- 是否存在写死的经验参数其实应该改成方向性判断？
- 是否存在大众营销话术式的空洞句子（“提升吸引力”“引发共鸣”这类无法指导决策的词）？
- 金句是否经过事实/逻辑检验？
- 是否存在未经确认却被写成事实的内容？
- 文稿是否能让一个没参与对话的人直接理解“要做出什么作品”？
- 下一步执行者能否从文稿拿到继续工作所需的信息？

## 修改与自检纪律

- 诊断先行：只修改真正有问题的地方，不因为某个词“像 AI 写的”就整段重写。
- 事实边界：已确认 / 推导（注明是归纳）/ 无法确认（明确说无法确认，不用“看起来合理”的版本填充）。
- 用户否定过的写法（详见 `references/writing-methodology.md` 第 11 节）优先作为检查项，而不是事后等用户再否定一次。
