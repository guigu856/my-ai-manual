# 想法 → 可发布的小红书图文作品

## 作用定位

输入：原始想法、观点、观察、聊天记录、文章、脚本、字幕、笔记、已有小红书文案或已有卡图。

输出：一个完整的小红书图文作品包，而不是只给文案建议或页面草稿。

默认交付：

```text
<task-dir>/
├── work-brief.md
├── page-plan.md
├── post.md
├── index.html                 # 使用 HTML/CSS 路线时
├── assets/                    # 用户素材、生成图或有来源记录的网络素材
├── output/
│   ├── xhs-01.png
│   ├── xhs-02.png
│   └── ...
├── preview/
│   └── contact-sheet.jpg
└── qa-report.md
```

成品只有在内容、视觉、移动端阅读和技术检查完成后，才称为“可直接发布”。

## 边界

- 本 Skill 负责静态小红书图文作品：封面、多页卡图、标题、正文、话题和质检。
- 只写文案且不要出图时，交给 `idea-to-platform-content`。
- 视频笔记成片交给视频生产 Skill；本 Skill只可输出图文改编方案，不制作视频。
- 单张封面或纯图片编辑交给图像设计/编辑 Skill。
- 自动登录、上传、保存草稿和发布不在本 Skill范围内；需要发布器时另行明确授权。
- 不把“爆款”“高转化”“涨粉”写成已保证结果。平台表现属于 `missing evidence`，除非有真实发布数据。

## 核心原则

1. **先守住观点，再做平台适配。** 平台化不能改变原文的主语、对象、因果和立场。
2. **一页只推进一个信息。** 卡片不是把长文切成等长段落，而是重建阅读推进。
3. **视觉必须解释内容。** 比较、流程、层级、因果、边界和状态变化优先用对应结构表达；装饰不能冒充信息。
4. **标题、卡图和正文是同一作品。** 三者承诺一致，不用封面制造正文没有兑现的冲突。
5. **先修源文件，再整组重渲。** 不在最终 PNG 上逐张打补丁。
6. **检查后再声称可发布。** 预览图存在不等于通过发布门禁。

## 工作流

### Gate 1：确认输入与作品目标

从上下文提取：

- 原始材料及其可信度
- 用户真正要表达的一句话
- 目标读者和阅读场景
- 观点型、教程型、比较型、清单型、故事型或证据型
- 是否已有图片、截图、品牌色或现成卡图
- 用户明确禁止的说法和视觉风格

上下文已足够时直接执行。只有缺失信息会改变作品结构时才询问。

没有任何图片且内容确实需要图片时，只询问一次素材路线：

- A：用户提供照片/截图
- B：检索网络素材并记录来源
- C：生成原始视觉素材

抽象观点可以使用功能性图形、排版关系和语义结构，不强制塞入图片。

读取 `references/content-routing.md` 完成形态判断。

### Gate 2：锁定内容契约

生成 `work-brief.md`，至少写明：

- 核心观点
- 读者看完后应记住的一句话
- 已确认事实
- 用户原始判断
- 推导内容及其证据边界
- 禁止改写的主语、对象、因果和边界
- 作品类型、预计页数和视觉语法

如果核心观点无法从原始材料中还原，先回到材料定位，不用常见的小红书话术补空白。

### Gate 3：规划阅读推进

读取 `references/card-story-architecture.md`，生成 `page-plan.md`。

每页计划包含：

```text
页码 / 页面职责 / 核心句 / 信息增量 / 视觉关系 / 素材 / 与前后页的连接
```

默认结构不是硬模板。根据内容选择：

- 观点型：冲突 → 区分 → 机制 → 误区/边界 → 价值 → 提问
- 教程型：结果 → 前提 → 步骤 → 检查点 → 常见错误 → 清单
- 比较型：共同问题 → 维度 → 差异 → 适用边界 → 选择建议
- 故事型：场景 → 变化 → 关键发现 → 重新理解 → 留给读者的问题
- 清单型：使用场景 → 分类 → 条目 → 选择规则 → 汇总

通常使用 5–9 页。超过 9 页时检查是否能合并，超过 12 页时优先改成长笔记或拆成系列。

### Gate 4：写卡片文案和发布文案

同时完成：

- 封面标题
- 每页标题与正文
- 小红书标题
- 发布正文
- 话题标签
- 必要的互动问题

规则：

- 保留作者原有语气，不把观点统一改成营销腔。
- 删除无来源的“所有人都”“大多数人都”“已经爆火”等群体断言。
- 不用机械排比、空洞拔高和每页一句“金句”的强迫整齐。
- 封面标题只承诺正文实际解释的内容。
- 互动问题应承接观点，不用无关的“你怎么看”。
- 卡片承载结论、比较、步骤和证据；细节与补充放进 `post.md`。

### Gate 5：选择视觉系统并生产

读取 `references/production-and-rendering.md`。

默认小红书卡图为 1080×1440 PNG（3:4）。精确平台限制属于易变信息；用户要求“最新”“当前上限”或涉及自动发布接口时，先查官方来源再执行。

执行适配顺序：

1. 若已安装 `guizang-social-card-skill`，可调用其种子模板、版式路由和浏览器渲染流程。
2. 若有其它稳定的 HTML/Markdown 卡片渲染器，可在满足本 Skill输出契约的前提下使用。
3. 没有专用渲染器时，使用本地 HTML/CSS + 真实浏览器截图；不把 Markdown 预览截图当最终卡图。

视觉规则：

- 一个作品包只使用一个视觉系统和一个主锚点色。
- 大标题、正文、页码和页脚保持稳定的空间锚点。
- 每页至少有一个明确的视觉职责：比较、流程、层级、警示、证据、结论或提问。
- 正文在手机缩小后仍可读；放不下时先删字或换版式，不缩到不可读。
- 生成图片只生成无文字的原始视觉素材；中文标题和正文使用确定性排版。
- 网络素材保存来源 URL；不把未知版权状态写成“可商用”。

### Gate 6：渲染与预览

从源文件整组渲染 PNG，并生成 contact sheet。

渲染后至少检查：

- 每张图片尺寸和文件格式
- 封面在 360px 宽预览下是否仍能读懂
- 每页是否存在文字溢出、孤行、尴尬断词和页脚碰撞
- 全组是否重复同一版式或出现无意跳位
- 页面下部是否留下未经设计的大面积空白
- 视觉是否在解释原文，而不是只做装饰

发现问题时修改 `page-plan.md`、HTML/CSS 或原始视觉素材，然后整组重渲。

### Gate 7：发布前质检

读取 `references/quality-gates.md`，生成 `qa-report.md`。

运行确定性包检查：

```bash
python scripts/validate_xhs_package.py <task-dir>
```

如果使用的渲染 Skill带 DOM 级校验器，再运行对应检查。只有以下条件都满足才标记 `publish-ready`：

- 内容主线与原始材料一致
- 页面推进没有重复或断层
- 标题、卡图、正文承诺一致
- 每张输出尺寸正确且可打开
- 没有可见溢出、截断、错别字和尴尬换行
- contact sheet 已检查
- `qa-report.md` 记录检查结果和未解决问题

有未解决问题时标记 `preview-ready`，并列出具体页码和修复动作。

### Gate 8：交付

交付时给出：

- 输出目录绝对路径
- 卡图数量、尺寸和顺序
- contact sheet
- `post.md`
- `qa-report.md`
- 使用的渲染路线
- 素材来源和仍需用户判断的版权事项
- 状态：`publish-ready` 或 `preview-ready`

不要把制作过程、失败记录或内部工具术语写入受众可见卡片。

## 修改已有作品

用户要求修改现有图文时：

1. 先检查全部页面、标题、正文和源文件。
2. 明确问题属于内容、结构、视觉、排版还是平台适配。
3. 修改最上游的责任文件。
4. 整组重渲并重新生成 contact sheet。
5. 重新执行 Gate 7，不沿用旧的通过结论。

## 失效规则

- 用户材料只有一句话但缺少关键主张时，不把常见行业观点伪装成用户观点。
- 涉及新闻、价格、政策、产品参数、平台规则和统计数字时，先核实来源。
- 没有真实证据时，不编造案例、数据、用户评价、效果对比和使用体验。
- 视觉渲染依赖缺失时，仍交付完整 `work-brief.md`、`page-plan.md` 和 `post.md`，状态标记为 `render-blocked`，不把未生成的 PNG 写成已交付。
- 发布账号、Cookie、Token 和密钥不写入作品包、日志、README 或报告。
