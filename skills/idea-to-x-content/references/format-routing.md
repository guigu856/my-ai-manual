# X/Twitter 发布结构路由

根据内容密度、论证关系、账号限制和用户指定格式，选择最合适的发布结构。

## 1. 路由优先级

1. 用户明确指定格式时，直接使用指定格式。
2. 用户明确标准账号 / 非 Premium 时，把当前单帖发布限制作为硬约束。
3. 用户未指定格式时，按内容结构选择，不默认生成 Thread。
4. 平台字符计数属于易变参数；能核验时使用当前官方规则，不能核验时采用更短的发布单元，不声称精确字符合规。

## 2. 单条推文

适用：

- 只有一个核心判断
- 不需要连续论证
- 一个机制、边界或行动含义即可解释清楚

结构：

```text
核心判断
必要解释 / 机制 / 边界
可选的行动判断
```

要求：

- 开头直接进入内容
- 一条只讲一个主观点
- 不用后半段重新总结前半段
- 没有必要时不加 CTA、话题标签或链接

## 3. 主帖 + 回复链

适用：

- 一个总判断下面有多个并列原则
- 用户使用标准账号，单条无法完整承载
- 希望主帖先建立主题，后续逐条提供价值
- 内容更像“4 条原则 / 5 个误区 / 3 个判断标准”，而不是连续故事

结构：

```text
【主帖】
主题 + 最强判断 + 后续内容承诺

【回复 1】
第一个完整价值单元

【回复 2】
第二个完整价值单元

...

【结尾回复，可选】
只在存在新的收束判断时添加
```

主帖要求：

- 单独看也有价值
- 不只写“分享几点心得”
- 不把所有结论提前讲完
- 承诺的内容必须由后续回复兑现

回复要求：

- 一条一个原则或判断
- 每条新增信息
- 允许长度不一致
- 不重复主帖的 Hook
- 不为了保持整齐而强行使用完全相同的句式

结尾回复只有在能增加一个新的判断、决策规则或高密度收束时才保留。纯重复总结直接删除。

## 4. Thread

适用：

- 内容存在明显递进关系
- 前一条是后一条理解的基础
- 需要解释机制、因果链、方法过程或完整案例

结构：

```text
1/N：核心问题或关键判断
2/N：背景 / 第一层机制
3/N：继续推进
...
N/N：得到结论、边界或行动判断
```

要求：

- 每条仍应尽量可以单独理解
- 每条都有唯一新增信息
- 前后关系明确
- 不按原文段落机械映射
- 不把一句话能讲清的内容拉成多条

## 5. 清单式推文

适用：

- 检查项
- 工具清单
- 判断标准
- 简短原则集合

如果整份清单可以在单条中清楚表达，使用单条；如果每一项都需要解释，改用主帖 + 回复链。

禁止为了“看起来内容很多”把一句原则拆成多个同义项。

## 6. 脚本 / 长文拆解式 Thread

输入为口播稿、文章、长笔记或脚本时，先建立论证结构：

```text
核心命题
├── 支撑判断 A
├── 支撑判断 B
├── 机制 / 原因
├── 边界 / 反例
└── 行动含义
```

然后按论证单元生成推文。

禁止：

- 按原文每段对应一条推文
- 按固定字符数切块
- 保留所有原文细节
- 为了忠实原文而牺牲 X 的信息密度

保留的是核心信息和论证关系，不是原稿版式。

## 7. 自适应决策表

| 输入状态 | 首选格式 |
|---|---|
| 一个明确判断 | 单条推文 |
| 一个总判断 + 多个并列原则 | 主帖 + 回复链 |
| 连续机制 / 因果 / 方法 | Thread |
| 多个短检查项 | 清单式推文 |
| 长脚本 / 长文章 | 脚本拆解式 Thread |
| 非 Premium 且内容较长 | 主帖 + 回复链或 Thread |

## 8. 发布密度

每个发布单元至少承担一个明确功能：

- 提出判断
- 解释机制
- 给出边界
- 提供例子
- 提供行动规则

如果一个单元只承担“过渡”而没有新增信息，应和前后条合并。

## 9. 标记与复制

为了方便用户复制，可以在交付文本中使用：

```text
【主帖】
【回复 1】
【回复 2】
```

这些标签不是实际推文内容。若用户要求“纯正文”，移除全部标签，只用空行分隔发布单元。
