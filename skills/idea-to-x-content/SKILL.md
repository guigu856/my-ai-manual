# Idea to X Content

把一个人的原始想法或已有文稿，压缩、提炼并组织成高信息密度、可直接发布的 X/Twitter 内容。

本 Skill 的目标不是把原文“写得更像一篇文章”，而是找到其中最值得传播的判断、机制、方法或冲突，再为 X 选择合适的发布结构。

## 输入

至少提供以下之一：

- 一个观点、想法、观察或碎碎念
- 一段聊天记录或语音转写
- 一篇已有文案、文章或脚本
- 一条需要改写或扩展的推文

可选信息：

- 是否为标准账号 / 非 Premium
- 希望单条、Thread、主帖+回复链或其它形式
- 目标读者
- 是否需要先做观点价值诊断
- 是否保留原有语气
- 禁止使用的表达、词语或结构

用户已经给出足够上下文时直接执行，不重复询问。

## 核心原则

1. **先理解观点，再写推文。** 先确认用户到底在表达什么，不把相邻但不同的观点补进来。
2. **先判断价值，再优化措辞。** 一个大众化结论不会因为句子更漂亮就变得更有传播价值。
3. **不默认认同用户。** 观点存在错误前提、逻辑跳跃、过度归纳或缺乏证据时，必须先识别；可修正则修正，不可确认则降低断言强度。
4. **优先寻找信息增量。** 每一条推文都必须提供新的判断、机制、例子、边界或行动方法，不用不同措辞重复同一结论。
5. **一条推文只承担一个主要价值单元。** 长内容按论证单元拆，不按字数机械截断。
6. **格式由内容决定。** 单条能讲清就不强行 Thread；标准账号装不下时优先拆成主帖+回复链或 Thread。
7. **保留人的判断感。** 不把原始表达磨成标准知识博主腔，不为了“完整”补齐对称结构。
8. **默认交付可发布正文。** 用户没有要求分析过程时，不在成品前后附加解释、写作过程、模板说明或聊天式结尾。

## 工作流

### 阶段 1：还原真实观点

读取 `references/value-diagnosis.md`。

提取：

- 核心主张：用户最想让读者记住的一句话
- 对象：这句话在讨论什么具体问题
- 痛点 / 冲突：它针对什么真实摩擦
- 方法或判断：读者看完能获得什么新判断
- 证据状态：已确认事实、个人经验、合理推导、暂时无法确认

**Gate 1：** 能用一句话准确复述核心观点，且没有替用户新增主张。

### 阶段 2：做价值诊断

检查该观点是否具备至少一种可传播价值：

- 非显而易见的判断
- 对常见误区的纠正
- 明确的痛点命中
- 可执行的判断规则或方法
- 对一个机制、因果或失败模式的解释
- 有边界条件的经验结论

如果原始观点过于大众化，先从原文内部继续挖掘更具体的冲突、隐藏成本、错误激励、判断边界或反馈机制。不得为了“眼前一亮”制造用户没有表达过的反常识观点。

**Gate 2：** 最终选中的角度必须能回答“这条内容新增了什么”，不能只剩正确但空泛的常识。

### 阶段 3：选择发布结构

读取 `references/format-routing.md`。

优先级：

1. 用户明确指定格式：按用户格式执行。
2. 用户未指定：根据内容密度、论证关系和账号限制自动选择。
3. 用户明确非 Premium / 标准账号：把平台单帖限制视为硬约束，长内容拆分，不压缩到失去核心信息。
4. 平台字符规则属于易变参数；有条件时按当前官方规则核验，不在 Skill 中写死历史上限。

**Gate 3：** 每个发布单元都能独立理解，且整个结构存在明确推进关系。

### 阶段 4：写主帖

主帖承担以下任务之一：

- 直接给出最有价值的判断
- 点出具体痛点或反差
- 给出一个值得继续读下去的问题，并由后续回复兑现

禁止：

- 用日常铺垫占据主帖主要篇幅
- 只制造悬念，不提供价值承诺
- 为了制造冲突使用夸张、虚假的大众判断
- 用“今天突然想到”“最近越来越觉得”作为默认开头；只有个人经历本身是证据时才保留

### 阶段 5：展开价值单元

长内容按“论证单元”拆分：

- 一个原则
- 一个机制
- 一个误区
- 一个边界
- 一个例子
- 一个行动判断

每条只保留最必要的解释。后续回复不得重新讲一次主帖已经讲清的内容。

脚本或长文输入时，先提取论证结构，再生成推文；禁止按原文段落或固定字符数直接切块。

### 阶段 6：去 AI 味与语气校准

读取 `references/human-writing.md`。

处理顺序：

1. 保留信息和用户原有判断
2. 删除模板化句式和空洞拔高
3. 调整句长、节奏和结构，不追求所有段落整齐
4. 若用户提供过自己的写作样本，优先匹配用户真实写法
5. 不新增事实来制造“人味”

### 阶段 7：发布前检查

逐项检查：

- 核心观点是否仍然是用户原意？
- 主帖是否单独看就有价值？
- 每条回复是否新增信息？
- 是否出现无来源的“很多人都……”之类群体断言？
- 是否把个人经验写成普遍规律？
- 是否出现机械的“不是 A，而是 B”、三段式排比或刻意金句？
- 是否存在为了完整而添加的无效解释？
- 是否符合用户账号与当前平台发布限制？
- 是否可以直接复制发布？

所有阻断项清零后交付。

## 自适应输出模式

| 模式 | 使用条件 | 默认输出 |
|---|---|---|
| 单条推文 | 一个核心观点，单帖可完整承载 | 一条完整正文 |
| 主帖 + 回复链 | 多个并列原则、标准账号、希望主帖负责抓住主题 | 主帖 + 若干回复 |
| Thread | 存在连续论证、机制拆解或递进关系 | 1/N 到 N/N 或分条正文 |
| 清单式推文 | 规则、检查项、工具清单且信息量可控 | 一条或短链 |
| 脚本拆解式 Thread | 输入为长文、口播或脚本 | 按论证单元重构，不机械切段 |

用户没有要求多个版本时，只生成一个最合适的版本。

## 交付契约

默认只输出可复制发布的正文。

多条结构需要区分时，可使用：

```text
【主帖】
...

【回复 1】
...

【回复 2】
...
```

这些标签只用于帮助用户复制，不属于推文正文。

只有用户明确要求“先分析再写”时，才在正文前增加简短诊断，诊断必须区分：

- 已确认
- 合理推导
- 无法确认

| 需要 | 读取 |

| 去 AI 味、保留真实人类表达 | `references/human-writing.md` |

## 边界

- 本 Skill 只负责 X/Twitter 内容，不负责图片、视频、排版设计或自动发布。
- 需要跨平台一稿多改时，使用 `idea-to-platform-content`。
- 涉及实时数据、产品价格、政策、人物职位、平台规则等易变事实时，必须先核验；无法核验时不写成确定事实。
- 不制造虚假数据、虚假案例、虚假引用或虚假群体共识。
- 不把“更有冲击力”理解为更夸张。观点可以更尖锐，但证据边界不能变。
