# 叙事设计

本文件负责回答：这条视频到底要让谁，从什么认知走向什么认知。

## 一条视频只有一个主命题

先写出一句完整判断：

> 对于【目标受众】，这条视频要说明【核心观点】，因为【关键理由】，看完后观众应能【复述或行动】。

如果一句话无法说清，先缩小范围。不要把多个相关观点都塞进同一条短视频。

## 先定义认知变化

`BRIEF.md` 必须包含：

- `current_belief`：观众现在可能怎样理解
- `target_belief`：视频结束后希望怎样理解
- `belief_gap`：中间缺失的关键解释
- `emotional_shift`：从什么感受转向什么感受

观点视频的价值通常不是提供更多信息，而是改变解释框架。

## 叙事类型

不要强制所有视频使用“问题—解决方案—CTA”。根据内容选择一种主结构。

### reframe：认知重构

适合“你以为 X，其实 Y”。

```text
旧认知 → 旧认知为何看似合理 → 暴露矛盾 → 新解释 → 新判断
```

### causal-explanation：因果解释

适合解释某个现象为什么发生。

```text
现象 → 常见归因 → 隐藏变量 → 因果链 → 结论
```

### mechanism：机制讲解

适合解释一个系统如何运转。

```text
目标 → 输入 → 核心过程 → 输出 → 边界条件
```

### comparison：方案对比

适合比较方法、工具或认知方式。

```text
共同目标 → 对比维度 → A 的机制与代价 → B 的机制与代价 → 适用判断
```

### process：操作流程

适合教程或可执行方法。

```text
起点 → 步骤 → 每步判断条件 → 结果 → 常见失败点
```

### argument：观点论证

适合主张型内容。

```text
主张 → 理由 → 证据或例子 → 反例/边界 → 收束
```

### list-with-thesis：带主张的枚举

只有当多个项目共同支持一个结论时才使用。

```text
主结论 → 项目 1 → 项目 2 → 项目 3 → 共同规律
```

## Beat 的叙事职责

每个 Beat 必须至少承担一种职责：

- `hook`：提出值得继续听的问题或矛盾
- `orient`：建立讨论对象和上下文
- `claim`：提出判断
- `explain`：解释关系或机制
- `example`：把抽象判断落到具体情境
- `evidence`：提供数据、事实或可验证依据
- `contrast`：形成差异
- `reframe`：改变解释框架
- `boundary`：说明适用条件、反例或风险
- `payoff`：给出最终理解或行动

职责不是固定顺序。一个 Beat 可以有主职责和次职责，但不能没有职责。

## 节奏原则

- 重要性不等于时长平均分配。
- 铺垫应尽快建立必要上下文，不为了氛围拖延。
- 复杂机制需要更长稳定展示时间。
- 转折前可以留短暂停顿，转折后应给新判断落地时间。
- 结论不应在画面上提前完全泄露，否则削弱口播推进。

## 保留原文模式

当用户要求保留原稿：

- 可以调整停顿、字幕切分和场景划分
- 不改写事实判断、语气和核心措辞
- 发现口语不顺时标注建议，不静默篡改

当允许重写：

- 优先口语自然、短句、明确指代
- 删除重复铺垫和无法服务主命题的内容
- 不为了适配动画而扭曲观点

## Gate 检查

进入脚本拆解前必须能回答：

1. 谁会看？
2. 他们当前相信什么？
3. 视频要改变哪一个判断？
4. 最关键的解释缺口是什么？
5. 什么内容即使有趣，也应该删掉？
