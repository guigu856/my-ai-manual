# AI Note Resource Pack（AI 每期资料笔记）

把原始输入整理成一份有笔记感、能解释问题、又包含可复用资料的完整文档。

这不是把几个概念、步骤和提示词拼在一起。整篇必须沿着一条推导链前进：先把问题说清，再解释它为什么发生，然后根据原因推出解决方法，最后把方法沉淀成可直接使用的资料。

## 唯一产物

只输出：

```text
RESOURCE_NOTE.md
```

不要额外输出：

- 飞书入口页或目录索引
- `META.json`
- 发布文案或群公告
- 多个拆分附件
- 飞书写入或知识库操作结果
- 原始输入、视频或飞书 URL 字段

用户明确要求其他文件时，再按用户指定增加；默认仍以一份资料文档为主体。

## 输入

至少提供一种：

- 原始问题、感想、碎片笔记或踩坑记录
- 一段已经形成的观点
- 对应短视频脚本
- 一份已有资料文档及修改意见

可选信息：期数、标题、作者口吻、希望沉淀的资料类型。

信息缺失时，从现有输入中提取能被证实的内容。不要为了填满模板编造用户的经历、情绪、失败尝试或因果。

## 固定文档结构

严格使用以下四节，不自行增加 4.1、4.2、4.5、4.6、总结、视频关系、相关期数等章节：

```markdown
# 第【期数】期｜【标题】

## 1. 我遇到的问题

## 2. 分析

## 3. 如何解决

## 4. 资料包
```

期数未提供时使用用户项目中的下一期；无法从上下文确定时写 `第【期数】期`，不猜数字。

标题应对应一个明确问题，优先使用「如何解决 + 具体问题」，不要写成空泛栏目名。

## 全文连续性

每一节必须承接上一节，不能分别摆放一堆概念。

### 1 → 2：从问题进入原因

第 1 节写清发生了什么，第 2 节紧接着解释这种现象为什么会出现。分析必须回应前文中的具体问题，不另起一个泛泛的知识科普。

可使用自然衔接：

- 「这个问题不只是……」
- 「真正影响结果的是……」
- 「问题出在……」

不要机械复制固定连接词；衔接应服务实际语义。

### 2 → 3：从原因推导方法

解决方法必须来自分析，而不是突然出现一套通用步骤。明确写出推导关系：既然原因是 X，那么方法就要针对 X。

可使用：

- 「既然……，那么……」
- 「要避免这个偏差，关键不是……，而是……」
- 「因此，回答前需要先……」

每个方法都能在第 2 节找到对应原因；找不到依据的方法应删除。

### 3 → 4：从方法沉淀资料

资料包是前面解决方法的可复用版本。不要在 `## 4. 资料包` 后直接甩出提示词、清单或 Skill。

先用一至三段说明：

1. 资料基于前文哪项分析、观察或方法整理而成；
2. 它适合放在哪里或用于什么任务；
3. 它最终被整理成什么资料类型。

然后用一句自然引入：

> 以下是整理后的【资料类型】：

再给资料本体。

## 各部分写作规范

### `## 1. 我遇到的问题`

写用户真实提供的问题或现象，让读者知道「在什么情况下，出现了什么偏差」。

- 保留第一人称笔记感，但不要编造感受。
- 用一至三段形成场景，不列抽象名词清单。
- 可以列出少量具体歧义或异常，但列表必须解释前面的现象。
- 不在本节提前给解决方案。

### `## 2. 分析`

解释 AI、工具、流程或表达为什么会产生前述问题。

- 标题固定为「分析」，不写「我的判断」「核心思路」。
- 区分已证实事实、基于输入的分析和尚未验证的推测。
- 不把近似现象写成绝对规律。例如中文并非没有逻辑关系；更准确的写法是中文经常省略主语、时态标记或连接关系，理解更依赖语境。
- 不为用户补心理动机，不编造演化史或未发生的尝试。
- 分析最后应自然引出第 3 节需要解决的关键缺口。

### `## 3. 如何解决`

把分析转化为能执行的方法。

- 标题固定为「如何解决」，不写「解决过程」「完整方法」。
- 开头明确承接分析，例如「既然 AI 缺少对真实场景意义的判断……」。
- 先解释解法逻辑，再展开步骤；不要一上来只列 1、2、3。
- 只保留真正影响结果的动作。
- 不为了显得严谨而制造额外确认。

涉及歧义判断时，遵守：

- 歧义存在不等于必须提问。
- 上下文已经能确定意思时，直接处理。
- 不同解释会得到相同回答或行动时，直接处理。
- 只有上下文仍不能排除多种解释，且解释差异会实质性改变回答、行动或结论时，才向用户确认。

### `## 4. 资料包`

先解释资料从何而来、放在哪里、什么时候用，再输出资料本体。

资料前置说明应类似：

```text
基于前面的分析，可以把【观察或方法】整理成【资料类型】。

本资料可用于【系统提示词 / 某类任务的附加判断 / 执行流程 / 检查环节】中，帮助【具体作用】。

以下是整理后的【资料类型】：
```

这只是逻辑示例，不要每期逐字套用。

## 资料类型判定

不要预设每期一定输出提示词。先从原始输入中提取「问题、原因、可复用动作」，再选择一个主类型；必要时可以在同一资料本体中加入一个辅类型，但不要拆成多个文件。

| 输入的核心用途 | 主类型 | 资料本体写法 |
|---|---|---|
| 复制后交给 AI 执行 | 提示词 | 完整可复制块；需要替换处使用 `【变量】` |
| 长期约束 AI 或团队行为 | 规则 | 按必须、禁止、条件判断组织 |
| 教智能体完成稳定多步骤任务 | Skill | 触发条件、输入、步骤、输出、边界 |
| 执行前逐项核对 | 检查清单 | 可勾选条目；每条对应前文风险 |
| 场景与做法需要快速匹配 | 速查表 | 场景 → 判断 → 做法 |
| 需要通过正反例理解差异 | 示例库 | 原写法 → 改进写法 → 原因 |

如果输入只是概念观察，暂时没有稳定可复用动作，就整理为简短规则或观察卡，不强行包装成复杂 Skill。

## 资料本体规范

- 提示词放在代码块中，保证可复制。
- 规则写清适用条件，不用「永远」「全部」掩盖边界。
- Skill 仅在已经存在稳定步骤时生成。
- 检查清单每一项都能回指第 2 节中的风险。
- 示例不编造事实，可使用明确标注的合成示例。
- 不把资料包重新拆成 4.1～4.6 等说明书式结构。

## 事实与歧义处理

写作前扫描：时序、主语、单复数、指代、逻辑、范围。

只有歧义会改变整篇资料的主题、分析方向或资料类型时，才暂停并确认最关键的一处。上下文已经明确时直接写，不要为了发现歧义而问。

外部事实、数字、模型机制或引言需要核实时，应先查证；无法核实时，用「可能」「在当前输入中表现为」等限定语，不伪装成已证实事实。

## 工作流

1. **提取原材料**：只记录输入中真实存在的问题、观察、原因线索和动作。
2. **锁定单一问题**：确保标题可以用「如何解决 X」表达。
3. **建立推导链**：问题 → 原因 → 针对原因的方法 → 方法的可复用形态。
4. **选择资料类型**：根据使用方式选择主类型，不根据形式偏好硬套。
5. **写 `RESOURCE_NOTE.md`**：使用固定四节结构。
6. **连续性复查**：逐节检查下一节是否真的由上一节推出。
7. **删减**：删除孤立概念、重复解释、多余小节和没有依据的建议。

## 交付前检查

- [ ] 只产出一份 `RESOURCE_NOTE.md`
- [ ] 正文只有四个固定二级标题
- [ ] 第 2 节解释了第 1 节的问题
- [ ] 第 3 节的方法能从第 2 节推出
- [ ] 第 4 节先说明来源、用途和类型，再给资料本体
- [ ] 资料类型来自输入用途，不是默认选择提示词
- [ ] 没有编造用户经历、心理、失败尝试或外部事实
- [ ] 没有为了发现歧义而机械提问
- [ ] 没有飞书操作、索引、META 或 URL 字段
