# 通用 MVP 规范与边界

## 一、MVP 的定义

MVP 是回答一个问题的最短路径：**你的问题是什么，最快的解决方案是什么？**

目的是验证一个核心想法能不能跑通。跑通的意思是：有一个东西，用户能操作，能看到结果。

## 二、核心原则

### 2.1 一个问题，一个闭环

MVP 只解决一个问题。这个问题要能用一句话说清楚。如果说不清楚，说明问题本身还没想明白，先理清问题再动手。

闭环的意思是：用户做了一个操作 → 看到了一个结果。这条路走通就是 MVP。

### 2.2 最少的步骤

从用户操作到看到结果，中间的步骤越少越好。每多一个步骤，就多一块代码，多一个改动点，多一个出错的可能。

如果一次调用能完成的事，不要拆成三步串行。拆步骤是优化阶段的事。

### 2.3 最少的概念

代码里的概念（类型、模块、数据结构）直接对应用户能感知的东西。用户感知不到的中间概念，MVP 阶段不建。

判断标准：如果删掉这个概念，用户的操作和结果不受影响，那 MVP 不需要它。

### 2.4 最少的技术

能用一个技术解决就不引入两个。能用文件存就不上数据库。能用 localStorage 就不上 IndexedDB。能不要后端就不要后端。

每引入一项技术，就多一层学习成本、调试成本和未来迁移成本。

### 2.5 不定死，留余地

MVP 阶段的设计应该是松的：文件少、结构浅、耦合低。这样改任何一处的时候，不会牵连其他地方。

具体来说：
- 数据结构字段尽量少，后续加字段比删字段容易
- 不做版本管理、迁移框架、历史记录这些基础设施
- 不做权限、多用户、云同步
- 规则写成一个文本/配置，改文本就改规则，不做规则管理系统

## 三、边界判断

### 3.1 什么属于 MVP

| 属于 MVP | 原因 |
|---|---|
| 核心操作闭环（输入 → 处理 → 输出） | 产品存在的唯一理由 |
| 让闭环跑通所需的最少 UI | 用户要能操作 |
| 让闭环跑通所需的最少数据结构 | 代码要能跑 |
| 让闭环跑通所需的最少技术依赖 | 技术是为闭环服务的 |

### 3.2 什么不属于 MVP

| 不属于 MVP | 原因 |
|---|---|
| 中间概念的细分拆解 | 用户感知不到，增加代码量和改动成本 |
| 数据库、迁移框架、schema 版本 | 基础设施过重，产品方向都没验证 |
| 个人数据管理（词库、历史、样本） | 沉淀类功能，前提是产品核心已经跑通 |
| 效果验证体系（评测集、对比试跑） | 质量优化手段，产品先存在才谈质量 |
| 版本管理、撤销恢复 | 稳定期功能 |
| 多步确认流程 | 增加交互复杂度，MVP 阶段先一步到位 |
| 竞品分析、借鉴落地优先级矩阵 | 文档工作量，MVP 阶段的精力应该在做东西上 |
| PRD 中大量的"非目标"、"风险矩阵"、"产品原则" | 团队协作文档，一个人做产品不需要写给别人看 |

### 3.3 判断公式

拿到一个功能或设计点时，问三个问题：

1. **删掉它，核心闭环还能跑通吗？** → 能跑通就不做
2. **它是优化现有体验，还是增加新能力？** → 优化的后置，MVP 先有再好
3. **做了它，改其他地方时会被牵连吗？** → 会牵连就不做，保持松耦合

## 四、MVP 的做法

### 4.1 开始之前

1. 用一句话写出你的问题
2. 用一句话写出你的解法
3. 确认解法能跑通的最短路径是什么（几步操作、几个页面、几次调用）

### 4.2 技术选择原则

| 场景 | MVP 选择 |
|---|---|
| 需要前端 | 用你熟悉的框架，一个页面起步 |
| 需要存数据 | 先内存或 localStorage，跑通再换 |
| 需要调外部服务 | 直接调，一个接口，一个配置项 |
| 需要后端 | 先问能不能不要后端。前端直连外部服务能跑通就不要后端 |
| 需要数据库 | 先问能不能用文件/localStorage。不能再用最轻的方案 |

### 4.3 代码结构原则

- 文件少，层级浅
- 一个功能一个文件，不提前按"领域层 / 应用层 / 基础设施层"分架构
- 类型定义直接写在用到的文件里，不提前建 schema 库
- 测试覆盖核心闭环的输入输出，不给中间函数写单元测试

### 4.4 迭代节奏

MVP 做完之后，根据实际使用中发现的问题决定下一步做什么。迭代方向来自真实使用，来自"我用了之后觉得哪里不行"，来自具体的体验缺口。

不要在 MVP 阶段就规划 V0.2、V0.3、V1.0 的功能列表。规划是猜测，使用是事实。

## 五、常见的 MVP 膨胀模式

以下是容易掉进去的坑，做之前对照检查：

| 膨胀模式 | 表现 | 修正 |
|---|---|---|
| 概念先行 | 还没写代码就定义了 5+ 个领域类型 | 从用户操作出发，操作涉及几个东西就定义几个 |
| 流程串行化 | 把一次能完成的事拆成多步中间确认 | 先做一步到位，确认体验有问题再拆步 |
| 基础设施先行 | 先建迁移框架、版本管理、测试体系 | 先让功能跑通，测试只覆盖核心路径 |
| 防御性设计 | 考虑所有边界情况、冲突、异常恢复 | MVP 阶段先走通正常路径，异常处理做最简提示 |
| 文档先行 | PRD 写了几千字，代码还是空的 | 问题和解法各一句话，直接动手 |
| 参考过多 | 调研了 5 个竞品，每个写了借鉴方案 | MVP 不需要竞品分析，先做你自己想做的东西 |

## 六、适用范围

这份规范适用于：
- 一个人或极少人做新产品的起步阶段
- 产品方向还没被市场验证，核心假设还没被证实
- 目标是快速出第一版，通过实际使用发现问题和方向

当产品进入稳定迭代期（核心闭环已验证、有明确的用户反馈、需要扩展功能），这份规范的约束可以逐步放宽，引入更多结构和基础设施。
