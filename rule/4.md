# 代码逻辑与质量规范 (Coding Logic & Quality Guidelines)

为了提升代码的可读性、可维护性及健壮性，本工程在逻辑实现和代码质量上遵循以下规范：

## 1. 函数粒度约束 (Method Granularity Control)

严格遵循 **"小而美"** 的方法设计原则。

- **重构触发点**：当一个方法的业务逻辑步长过长、嵌套过深或分支过多（如过多的 `if-else` 或 `switch`）时，必须进行重构。
- **目录式设计**：主流程方法应像 **"书名目录"** 一样清晰。它应当仅包含高层级的逻辑流转，具体的实现细节应隐藏在语义化的私有辅助方法中。
- **单一职责**：每个辅助方法应只负责一项具体的、微小的任务。

## 2. 魔法值零容忍 (Magic Number Elimination)

严禁在业务逻辑中直接出现硬编码的数字或字符串。

- **语义化定义**：所有具有业务含义的状态、类型、配置项或固定文本，必须根据使用场景定义为 **枚举（Enum）** 或 **静态常量（Constants）**。
- **自解释能力**：代码应当通过常量名或枚举项直接表达其意图，而不是让阅读者去猜测"1"或"SUCCESS"代表什么。
- **集中管理**：通用常量应在专门的常量类中管理，模块私有常量可在对应类中定义。

## 3. 避免全限定符 (Avoid Fully Qualified Names)

严禁在业务逻辑中直接使用类的全限定路径（如 `new java.util.ArrayList()`）。

- **使用 Import**：所有外部类必须通过 `import` 语句引入，保持代码简洁。
- **解决冲突**：仅在出现类名冲突（如同时使用 `java.util.Date` 和 `java.sql.Date`）且无法通过重命名解决时，才允许对其中一个类使用全限定名。
